# AI Roadmap — плани розвитку мозку ворога

Жива мапа того, що зроблено і куди рухаємось із ШІ ворогів-учнів.

## ✅ Зроблено

| Етап | Суть |
|---|---|
| **v1 — Perceptron** | Одношаровий нейрон, лінійний. Імітував chase-формулу. |
| **v2 — MLP + backprop** | Прихований шар + зворотне поширення. Supervised-вчитель = перехоплення (interception). |
| **v3 — Q-learning + whiskers** | RL без вчителя: reward замість відповіді. 8 whiskers (зір на стіни), 8 дій. |
| **DQN-стабілізатори** | Target network + experience replay + error clipping → стабільне навчання. |
| **Decouple `IsLearner`** | Мозок вмикається прапорцем, а не міткою `Label` (separation of concerns). |
| **Трійця поведінки** | (1) proximity-reward за близькість стіни, (2) anti-stuck «фрустрація», (3) ε з автоспадом+floor. |
| **Феромони (стигмергія)** | Рій лишає сліди в глухих кутах і обтікає їх (deposit при застряганні / decay / repulsion). Реактивна колективна пам'ять, НЕ pathfinding. Паралельне читання + однопотоковий запис. Прапорець `pheromonesEnabled`. |
| **Спільний мозок (вулик)** | Поділ `Net` (мережа) / `Brain` (агент). Усі учні ділять один `Net` → колективний досвід, навчання в рази швидше, узгоджена поведінка («ключі»). `sync.Mutex` на спільний буфер + однопотокове навчання (`trainBrains`). Прапорець `sharedBrain`. |
| **Raycaster (1-ша особа)** | Опційний псевдо-3D вид (Wolfenstein-стиль): стіни через DDA, вороги-спрайти з z-буфером, позначені межі, FPS-керування. Клавіша `F`. Симуляція не змінюється — лише рендер. Деталі: [raycaster.md](raycaster.md). |
| **Метрики стенду** | «Міні-TensorBoard»: криві reward/TD-error + maxQ/ε у реальному часі (клавіша `G`). Тепер навчання видно, а не вгадується. |
| **Локальне сприйняття (POMDP)** | `localSight`: агент бачить гравця лише в межах `sightRange` і по прямій видимості (`hasLineOfSight`). Часткова спостережуваність → потрібна памʼять. Вхід `visible`. |
| **Памʼять (frame-stacking)** | На вхід — стек кадрів: `memFrames` слотів із кроком `stackSkip` (вікно ≈ `(memFrames−1)×stackSkip`). Агент памʼятає, куди зник гравець → жене за ріг. Крок від амнезика до POMDP-агента. |
| **Глибина (2 приховані шари)** | `56 → hidden1(32) → hidden2(16) → 8`. «Згин, потім згин ще раз» → складніші залежності (глибші заходи за кути). Backprop крізь 3 шари (ланцюгове правило двічі). |
| **Self-play (co-evolution)** | Гравцем керує мозок-жертва (`flee=true` → інвертований reward, та сама архітектура). Обидві сторони вчаться одночасно → гонка озброєнь (принцип AlphaZero). Спіймали → respawn, не game over. Мережа жертви ефемерна. Прапорець `aiPlayer`. Межа екрану стала суцільною стіною (прибрано wrap-around гравця). |
| **Метрики памʼяті** | `blind-chase` + `catch-rate` + ярлик конфігурації на панелі; клавіша `M` — скидання лічильників. Перша спроба кількісної бази — і, як з'ясувалось, забруднена: метрика зараховувала агентові рух ГРАВЦЯ. |
| **RNN/GRU — вивчена памʼять** | Рекурентний прихований стан `h` (мережа сама вчиться, що тримати) замість жорсткого вікна стеку. GRU-клітина + **BPTT** (sequence-replay + backprop крізь час) + burn-in. Прапорець `useGRU`. Заявлений тоді приріст `~55%→61%` **знято** — див. «Замір памʼяті» нижче. Лінія RNN(1997)→LSTM/GRU→Transformers. |
| **Бій: удар на швидкості** | Шкодить не дотик, а *closing speed* — проєкція швидкості на напрямок до цілі, асиметрично. Повільно зіштовхнулись = нічого; налетів = вкусив; лоб-у-лоб = обидва. **Hit-and-run стає оптимальним математично.** Поріг — частка ВЛАСНОГО максимуму (гравець швидший за рій). HP гравця, кадри невразливості, фракції + `friendlyFire`. |
| **Flow-field (pathfinding)** | BFS-хвиля від гравця → кожна клітинка знає напрямок до нього **крізь стіни**. Перебудова лише при зміні клітинки гравця. Візуалізація — клавіша `V`. Коректність доведена тестами (інваріант + прохід із кожної клітинки), а не оком. |
| **Рефакторинг мозку** | `brain.go` (1438 рядків, два світи в одному файлі) → ядро + `brain_stack.go` + `brain_gru.go`. Нуль змін поведінки. Стек-шлях свідомо лишено: baseline, fallback, предмет тестів. |
| **Командні бої** | Дві сторони з міксом типів: `Faction`+`WeightsFile` у конфізі, склад поля — `unitRoster`. Юніти гравця (`ConfigAllyChaser`/`ConfigAllyKiller`) полюють на найближчого ворога; вороги не змінені. **Multi-source BFS** дав по полю на сторону — без нього «свій вбивця» був би фікцією. Boids-сили фільтруються фракцією. |
| **Нагорода = власний внесок** | Знайдено приладом: крива рою мала розмах ±2.1 при стелі власного внеску ±0.6 — ~75% сигналу був рух ГРАВЦЯ, і знак нагороди перевертався залежно від його стилю. `progressToward()` тепер одне правило для всіх: проєкція ВЛАСНОЇ швидкості на потрібний напрямок. Виявилось, що фікс для вбивці був загальним принципом. |
| **Метрики по вуликах** | Рядок і крива на кожен тип мозку своїм кольором (раніше усереднювались різні масштаби нагород). `blind-chase` на власний прогрес; `qClip` 10→25 за формулою `r/(1−γ)`. |
| **Вбивця — другий тип мозку** | Окремий вулик (свій `Net` + свій файл ваг) → зміни для нього не чіпають налаштований рій. **Flow-field як ВХІД** (не контролер): мережа не витрачає ємність на лабіринт, а вчить тактику. Бойова нагорода (шкода/вбивство). Прогрес міряється **вздовж коридору**, інакше нагорода штрафувала б за обхід. Склад поля — `unitRoster` + `Count`. |

Деталі реалізації — у [ai-brain.md](ai-brain.md).

> **Аналітика «спільний мозок + феромони»:** механізми ортогональні (окремі
> прапорці). Феромони доповнюють вулик тим, чого мозок не вміє: пам'ять
> конкретного місця (у стані немає координат) і **анти-стадність** — розщеплюють
> однаковий потік на кілька струменів у різні проходи. Тримати `frustrationRepel`
> малим, щоб не ламати формації. Терміни — у [ai-glossary.md](ai-glossary.md).

## 🔜 Наступне

### Замір памʼяті — ЗАКРИТО
Борг «перезняти `55% (стек) vs 61% (GRU)`» сплачено. Коротко: **памʼять працює, і
рій робить її зайвою.**

| `blind-chase` | сам | у рої з восьми |
|---|---|---|
| без памʼяті | 52.2% *(майже монетка)* | 59.8% |
| з памʼяттю | 55.4% | 59.2% |

Горизонт памʼяті (0.25с…3.0с) на результат майже не впливає, щільність семплів —
взагалі. GRU програє стеку й навіть конфігу без памʼяті, тому `useGRU = false`.

Дорогою знайдено чотири діри в приладі й побудовано **безголовий стенд**
(`bench_test.go`): десятки прогонів на конфіг за хвилини замість дев'яти хвилин
стояння в куті за одну точку. Повна історія — розділ «Як ми це виміряли» в
[ai-brain.md](ai-brain.md).

**Коли повертатись до памʼяті:** висновок «памʼять майже нічого не варта» дійсний,
**доки вороги ходять групами І ДІЛЯТЬ ОДИН МОЗОК** — перевага рою це не «канал
інформації в бою» (alignment/cohesion в учнів = 0, триматись нікого), а СПІЛЬНИЙ
БУФЕР ДОСВІДУ: вісім тіл з окремими мережами не кращі за одне (`p = 0.14`), а
спільний проти незалежних дає домінування 85%, `p = 4×10⁻⁵`. Зʼявиться одинак
(бос, сталкер, розвідник) — і памʼять стане для нього єдиним таким каналом. Тому
рекурентний шлях у коді лишаємо.

**Межа стенду:** він надійно міряє основний ефект (144 прогони) і НЕ здатен міряти
модуляції малого основного ефекту. Пʼять гіпотез про те, що керує внеском памʼяті
(вікно, щільність, темп GRU, γ, зір), дали «різниці немає» — але для взаємодії на
ефекті +16 пунктів при похибці ±8.4 потрібно ~1200 прогонів на комірку, тобто 3–4
доби рахунку. Правильне формулювання там — «прилад не розрізняє», а не «спростовано».

**GRU перевірено окремо і на одинаку:** нерозрізненний від відсутності памʼяті
(домінування 52% при `lr 0.002`, 44% при `lr 0.005`; `p = 0.76` і `0.37`). Гіпотезу
«недонавчений» відкинуто — подвоєння темпу не дало нічого. Найімовірніша причина:
`seqLen = 8` кадрів = **0.067 с** розгортки BPTT проти потрібних задачі ~1.5 с, тож
градієнт не дістає до корисної інформації. Дешевий фікс на перевірку — подавати GRU
кожен ~20-й кадр (той самий трюк, що `stackSkip`), тоді 8 кроків накриють 160 кадрів.

### БОС-ОДИНАК ← ДОДАНО (поки на стеку, не на GRU)
`ConfigBoss`: `Count: 1`, власний `bossFile` (окремий вулик виникає сам), `MaxHP: 25`,
`CombatReward: true`, **`UsesFlowField: false`**. Останнє критично: із полем він завжди
знає шлях до цілі, і памʼяті нічого робити — вийшов би ще один вбивця. Живучість тут
умова НАВЧАННЯ, а не лише баланс: власна мережа з одним тілом набирає досвід у вісім
разів повільніше за вулик, тож бос мусить виживати, щоб узагалі вчитись. Ваги в
окремому файлі → накопичується через усі сесії й не забуває.

Свідомо НЕ на GRU: рекурентний шлях у поточному тюнінгу нерозрізненний від відсутності
памʼяті, тож бос вийшов би гіршим за звичайного юніта рою. Стек — єдина конфігурація
памʼяті, яку ми довели на одинаку (65%, `p = 0.004`).

Різницю між `4/10` і `2/180` не закладаємо: вона нижча за роздільну здатність стенду
(`p = 0.50`), тож бос бере глобальний стек-конфіг.

### Контракт памʼяті → властивість мережі ✅ ЗРОБЛЕНО
Був блокер: `useGRU` — глобальний прапорець, і `Step`, і `train` дивились на нього, тож
дати босу GRU, а рою стек було **неможливо** — усе або ніщо.

Тепер шлях памʼяті й форма входу живуть у `Net` (`memContract`), а `UnitConfig` має
`Memory` / `MemFrames` / `StackSkip`. Глобалі лишились **дефолтами** для типів, які
нічого не вказали, і для мереж без конфігу (мозок-жертва в self-play, тести).

Саме на мережі, а не на мозку: ваги навчені під ОДНУ форму входу, і всі мозки вулика
зобовʼязані її шанувати. А вулик ключується по `WeightsFile` →
**один файл = одна мережа = один контракт.** Поняття вже існувало — глобалі його
порушували.

**Заразом закрито справжній латентний баг.** `loadNetFrom` валідував архітектуру, але не
контракт памʼяті. Отже можна було мовчки завантажити GRU-навчену мережу на стек-шлях:
файл проходив валідацію (у ньому обидва набори ваг), але `W1/W2/W3` лежали на випадковій
ініціалізації — GRU-навчання їх не торкалось. Жодного попередження, просто випадкова
політика. Ми робили саме це під час GRU-експериментів. Тепер контракт пишеться у файл і
перевіряється; старі файли без нього приймаються, тож накопичені ваги не знецінились.

Видимий слід рефакторингу — на панелі метрик: ярлик памʼяті переїхав із спільного рядка
**у рядок кожного вулика**. Раніше `mem:stk stk4/10` малювалось раз на всю панель, і це
буквально показувало, що різні типи фізично не могли мати різну памʼять.

### Важіль BPTT ← ЗРОБЛЕНО, гіпотезу СПРОСТОВАНО
Реалізовано прорідження рішень (`memContract.gruSkip`): GRU оновлює `h` і обирає дію раз
на N кадрів, між ними дія повторюється, нагороди за інтервал сумуються з дискаунтом, а
ціль використовує `γ^N` (n-step return). Ті самі 8 кроків розгортки накривають 8N кадрів
без подорожчання BPTT.

**Не змінило нічого.** Домінування між важелями 0.067с / 0.33с / 1.33с / 2.67с — 44–56%,
тобто в межах шуму:

| Конфіг | n | медіана |
|---|---|---|
| стек `2/180` (еталон) | 24 | **54.2%** |
| GRU крок 1 (0.067с) | 24 | 52.2% |
| GRU крок 5 (0.33с) | 24 | 51.7% |
| GRU крок 20 (1.33с) | 24 | 51.2% |
| GRU крок 40 (2.67с) | 24 | 52.1% |

| Порівняння | n | домінування | p |
|---|---|---|---|
| стек проти **всіх** GRU | 24 / 96 | 65% | 0.026 |
| **всі GRU проти «без памʼяті»** | 96 / 72 | **47%** | **0.45** |

### ГОЛОВНЕ: це вже не «задача не потребує памʼяті»
Раніше так і тлумачили. Тепер так сказати НЕ МОЖНА: та сама задача, та сама нагорода, ті
самі входи — і **стек витягує реальні +2 пункти** (65%, `p = 0.004` на 48 прогонах), а
**GRU витягує нуль** (96 прогонів, `p = 0.45`). Отже справа в рекурентному шляху
конкретно, а не в задачі.

Усі налаштування вичерпані: темп навчання (2 значення, `p = 0.32`), важіль BPTT
(4 значення, 44–56%). Плюс симптом, який ми весь час недооцінювали: `maxQ ≈ 0` у GRU
проти 1.25–1.67 у стека — мережа тренується, але оцінки цінності не покидають
ініціалізації.

**Найімовірніший діагноз — БАГ У РЕАЛІЗАЦІЇ, не тюнінг.** Шість незалежних конфігурацій,
усі рівно на «немає памʼяті», при тому що альтернативний шлях на тій самій задачі працює.
Це підпис непрацюючого градієнта.

`TestGRULearnsSequence` цього не ловить: він перевіряє лише, що `Q` обраної дії ЗРОСТАЄ на
одному синтетичному відрізку, тобто знак сумарного оновлення. Він пройшов би й з
неправильним градієнтом reset-ворота або рекурентного звʼязку `Uh` — прямий шлях
`Wh·x` + `Wq·h` сам дав би те зростання.

### Числова перевірка градієнта ✅ ЗРОБЛЕНО — БАГА НЕМА
`TestGRUGradientMatchesFiniteDifference` порівнює `tdUpdateSeq` зі скінченними різницями
по **всіх одинадцяти групах ваг**. Усі в межах допуску; найгірший випадок використовує 37%
допуску на градієнті величиною `7e-5`, де панує шум `float32`.

Контрольний сигнал, що перевіряє сам тест: похідна по `Bq[a]` мусить дорівнювати кількості
кроків з дією `a`, помноженій на `td`. У відрізку кожна з 8 дій зустрічається точно раз,
`td = +1` → очікується рівно `1`. Отримано `1.000000` проти `0.999999`.

Три пастки, через які наївна перевірка дала б ФАЛЬШИВИЙ баг (усі обійдені й описані в
тесті):
1. BPTT навмисно **обрізана** на `seqBurnIn` — числову похідну теж рахуємо з фіксованого
   `h` на вході вікна;
2. `dhPrev` кліпається `gruGradClip` — свідоме відхилення від градієнта, на час перевірки
   кліп вимикаємо;
3. **semi-gradient**: `td` — константа, тож диференціювати треба `J = Σ td_t·Q_t(a_t)`, а
   не `½err²`.

Плюс ризик власної помилки знято трюком: нагорода ±50 при `qClip = 25` гарантує сатурацію
`td` до ±1, тож обчислення цілі переписувати не довелось — форвард беремо продакшеновий.

Перший прогін перевірки «знайшов баг» у reset-воротах (розбіжність 5.5%) — і це була вада
КРИТЕРІЮ: відносна похибка на градієнтах ~1e-4 безглузда при абсолютній розбіжності 8e-6.
Виправлено на стандартне комбіноване правило `|num−ana| ≤ abs + tol·max(...)`.

### GRU: питання ЗАКРИТО (структурно, не багом)
Вичерпано все:

| Гіпотеза | Як перевірено | Результат |
|---|---|---|
| темп навчання | 2 значення, 24 прогони | `p = 0.32` — без різниці |
| важіль BPTT | 4 значення, 0.067с…2.67с, 96 прогонів | 44–56% — без різниці |
| баг у градієнті | числова перевірка, 11 груп ваг | **градієнт правильний** |

При цьому стек на **тій самій** задачі витягує реальні +2 пункти. Отже лишаються дві
структурні причини, і жодна не є багом:

**1. Стеку памʼять ДАЮТЬ, а GRU мусить її ВІДКРИТИ.** Коли ціль не видно, кадр майже весь
нульовий (позиційні слоти обнулені). Стек отримує старіший кадр із видимою ціллю **прямо на
вхід** — «памʼятати» не треба вчитись узагалі, треба лише навчитись читати слоти 16–31. GRU
же мусить: розпізнати, що кадр був зрячим, закодувати напрямок, утримати його крізь десятки
оновлень, поки update-ворота підмішують нові (сліпі, майже нульові) кадри — і все це під
нагородою, що прийде багато кроків пізніше. Якісно важча задача оптимізації за ті самі
+2 пункти.

**2. Stored-state problem недолікована.** Відрізки в replay стартують із `h = 0` і мають
лише `seqBurnIn = 4` кроки прогріву, а в живого агента `h` накопичувався тисячі кадрів.
Розподіл `h` під час навчання ніколи не збігається з розподілом під час дії. Це відома
проблема (R2D2 її і досліджує), і 4 кроки прогріву для неї коротко.

**Рішення: припиняємо.** Стеля виграшу +2 пункти не варта проєкту рівня R2D2. Але код GRU
тепер **перевірений числово** — це та частина роботи, що не знецінюється: якщо колись
повернемось (задача з довшою памʼяттю, бос із рідкісною нагородою), реалізацію можна одразу
виключити з підозр і йти прямо до структурних питань.
Єдиний контекст, у якому памʼять за нашими ж замірами щось важить. Перевага рою — це
спільний буфер досвіду, а не тіла; одинак цього каналу позбавлений, і памʼять для нього
стає єдиним джерелом інформації про зниклу ціль (+2.5 пункти, `p = 0.001`).

Функціонал уже є: `useGRU`, окремий вулик через `WeightsFile`, `Count` у конфізі.
Що врахувати з виміряного:
- GRU у поточному тюнінгу нерозрізненний від відсутності памʼяті; темп навчання тут
  ні до чого (перевірено). Неперевірена причина одна — **важіль BPTT**: `seqLen = 8`
  кадрів це 0.067с при 120 TPS проти потрібних задачі ~1.5с. Фікс на перевірку:
  подавати GRU кожен ~20-й кадр (n-step, сума нагород + `γ^n`).
- босу потрібен **власний вулик** (свій `WeightsFile`), інакше він ділитиме досвід із
  роєм і ми знову не побачимо внеску памʼяті.
- міряти його треба стендом (`bench_test.go`, `units: 1`), а не оком.

### КОЛИ ПОВЕРТАТИСЬ ДО GRU — ознаки задачі й передумова

Питання закрито не «назавжди», а **для цієї задачі**. Ось за якими ознаками впізнати
задачу, де рекурентна памʼять окупиться, щоб через півроку не відновлювати логіку з нуля.

**Чому саме тут не окупилась.** Не тому, що задача проста. Тому, що потрібна їй памʼять —
**коротка й позиційна**: «де ціль була кілька секунд тому». Це рівно те, що фіксоване вікно
віддає ЗАДАРМА — старіший кадр лежить на вході, і мережі лишається навчитись читати слоти
16–31. GRU же мусить ту саму інформацію **відкрити й утримати сам**.

#### Чого фіксоване вікно не вміє в принципі

Вікно представляє **знімки**. Воно не може виразити чотири речі — і саме вони є показанням
до рекурентної памʼяті:

| Властивість | Приклад | Чому вікно не може |
|---|---|---|
| **тривалість** | «я не бачив ціль ДОВГО» | знімок скаже «на кадрі −180 порожньо», але не «порожньо вже дві хвилини» |
| **агрегат** | «цей гравець ЗАЗВИЧАЙ тікає вліво» | вікно тримає сирі кадри, а не висновки з них |
| **засувка (latch)** | «мене поранив ЦЕЙ супротивник» | вікно забуває рівно через `memFrames × stackSkip`, хоч би що там було; `update`-ворота GRU тримають біт невизначено довго |
| **дешевизна на довгих горизонтах** | памʼятати 10 секунд | вікно мусить або грубішати кроком (пропустить події), або товстішати кадрами (лінійно більший вхід → гірша вибіркова складність). `h` — 32 float за будь-якого горизонту |

#### Скільки видів памʼяті ми вже зробили РУКАМИ

Це найсильніший довгостроковий аргумент за GRU в цьому проєкті — і він не про
переслідування по коридору:

| Механізм | Яку памʼять підмінює |
|---|---|
| **flow-field** | «як пройти туди, куди я не бачу» |
| **феромони фрустрації** | «я вже застрягав у цьому місці» |
| **`stuckCounter`** | «я тисну в стіну вже N кадрів» |
| **стек кадрів** | «де ціль була щойно» |

Кожен — рукотворний фрагмент памʼяті, доданий тому, що мережа його не вивчила. **Робоча
рекурентна памʼять — це рівно те, що дозволило б їм стати вивченими замість
запрограмованих.**

Задачі, де він окупився б: бос із фазами («розлютився після 10 шкоди» — засувка); сталкер,
що вчить твій маршрут (агрегат за хвилини); агент, який памʼятає, де вже шукав (зараз це
феромони, тобто памʼять у середовищі, а не в голові); моделювання супротивника («цей
гравець ухиляється вліво»).

#### ПЕРЕДУМОВА: наша нагорода видає відповідь

`progressToward` рахує прогрес від **істинного** напрямку до цілі — навіть на сліпих
кадрах. Ми зробили це свідомо, щоб сліпі кадри не лишались без сигналу (див. ai-brain.md).
Наслідок, якого ми тоді не побачили: **реактивна політика отримує щільний градієнт
щокадру, і памʼять їй майже не потрібна.**

Тобто ми самі побудували нагороду, що робить памʼять зайвою. Для того, щоб навчання взагалі
пішло, це був правильний вибір — але це частина відповіді на «чому GRU не окупився».

**Найдешевший спосіб колись перевірити GRU по-справжньому — не міняти архітектуру, а
РОЗРІДНИТИ НАГОРОДУ.** Бос лише з бойовою нагородою («завдав шкоди»), без щільного
«наближайся»: агент мусив би зшивати довгі проміжки без сигналу, і саме там рекурентний
стан і довге призначення заслуг починають важити.

#### Чого НЕ робити

- **Не просто вмикати `Memory: MemoryGRU`.** Виміряно: нерозрізненно від відсутності
  памʼяті на 96 прогонах. Без зміни задачі це дасть босу гіршу памʼять, ніж стек.
- **Не піднімати лише `seqBurnIn`.** Проблема не в тому, що прогріву мало, — а в тому, що
  він стартує з `h = 0`, а живий агент має `h`, накопичений тисячами кадрів. Скільки б не
  прогрівався з нуля, у ту область простору станів не потрапиш. Треба **зберігати справжній
  `h`** разом із відрізком, а це зміна структури буфера.
- **Не підозрювати реалізацію.** Градієнт перевірено числово по всіх 11 групах ваг
  (`TestGRUGradientMatchesFiniteDifference`). Починати треба зі структурних питань.

#### Ціна повного лікування (щоб оцінка була під рукою)

R2D2-стиль: зберігати `h` з моменту дії + довгий прогрів (у них 40 burn-in + 80 навчальних
проти наших 4 + 8) + прийняти representational drift. Наш GRU уже **вшестеро дорожчий за
стек** на тік (1060 мкс проти 168); відрізки по 120 кроків замість 12 — ще **вдесятеро**
BPTT і памʼяті. Разом **близько 60× дорожче за стек** — за стелю **+2 пункти**, і то лише
для одинака. Саме ця пропорція і є причиною припинити.

### РЕСПАУН ✅ ЗРОБЛЕНО — і він розблокував бій у стенді

`UnitConfig.Respawns`: `0` = не повертається, `n` = n разів, **негативне = безкінечно**.
Безкінечний потрібен не для гри, а для **замірів**: стала популяція означає, що знаменник
метрик не пливе, і прогін, у якому пощастило вижити, порівнюється з прогоном, де юнітів
вибили.

**Респаун ОЖИВЛЯЄ той самий юніт, а не створює нового.** Це не оптимізація: `m.agents` у
метриках ключується вказівником на `Brain`, тож новий `Brain` на кожну смерть роздував би
«ag» до кількості СМЕРТЕЙ замість кількості юнітів. Ми вже ловили це на рестартах — один
стражник після трьох смертей читався як «4 ag».

Памʼять агента при відродженні скидається (`resetForNewLife`), і найважливіше там
**`hasPrev = false`**: інакше наступна нагорода порівняла б стан ПІСЛЯ відродження зі
станом ПЕРЕД смертю, і в буфер досвіду ліг би перехід через межу смерті, якого у світі не
існувало.

Повертається юніт **на свій пост** (`SpawnX/SpawnY`), а не в випадкову точку: для стражника
«повернувся на місце» — правильна поведінка, і гравцеві передбачувано.

### ТЕРМІНАЛЬНИЙ ПЕРЕХІД ✅ ЗРОБЛЕНО — смерть більше не безкоштовна

Знайдено при роботі над респауном: **смерть не доходила до нагороди.** Юніта видаляли
одразу, отже наступного `Step` він не отримував, і `dmgTaken` від фатального удару **ніколи
не ставав −2**. У нагороді просто не існувало причини не вмирати.

Для стражника, у якого бойова нагорода — ЄДИНЕ джерело сигналу, це означало, що половина
уроку зникала.

Тепер `transition.terminal`: ціль Беллмана для смерті — **лише нагорода**, без
`γ·maxQ(наступний стан)`, бо після смерті майбутнього немає. Доставляється в
`deathTransition` до будь-якого скидання стану.

**Лише стек-шлях.** У GRU нагорода живе у відрізках, і встромити термінальний крок посеред
відрізка складніше — там частковий відрізок відкидається. Наразі всі учні на стеку, тож це
покриває всіх; для GRU лишається боргом.

### Бій у стенді ✅ РОЗБЛОКОВАНО (`BENCH_COMBAT=1`)

Раніше бою в `tickHeadless` не було зовсім: удари вибивали учнів, респауну не існувало, і
на калібруванні це з'їло цілий прогін. Тепер респаун є, і бій вмикається прапорцем.

**Вимкнений за замовчуванням навмисно:** усі записані базові лінії (пул «без памʼяті» на 72
прогони, свіпи горизонту, зору, важеля BPTT) зняті БЕЗ бою, і тихо його ввімкнути означало
б їх знецінити — нові числа перестали б із ними порівнюватись.

Скриптований гравець у бойовому режимі ще й **атакує** (раз на `attackCooldownMax`),
інакше агенти з бойовою нагородою не отримали б жодної нагородної події.

Це відкрило те, чого досі не було: **стражника можна виміряти**. Що ми і зробили — чотири
рази, і всі чотири рази отримали нуль. Розділ нижче про те, чому.

## ⛔ Стражник: чотири нулі й одна причина

Питання було: **чи може стражник навчитись ловити вікна атаки й ухилятись?** Ми чесно
зміряли чотири ручки, по 24 прогони на комірку, з контролем валідності (`БЕЗ БОЮ: 0 з 24`
у кожній).

| ручка | частка виграних обмінів | домінування vs база | p | вердикт |
|---|---|---|---|---|
| **база** (×1, невр 45, шв 0.6) | **30.0%** | — | — | найкраща з чотирьох |
| γ 0.99 замість 0.95 | — | 49% | 0.902 | нуль |
| невразливість 20 (темп ×2) | 25.5% | 64% | 0.110 | нуль |
| ×4 стражники (спільний мозок) | 22.9% | 79% | 0.0006 | **гірше** |
| швидкість 1.2 | 7.2% | 100% | <0.0001 | **набагато гірше** |

Бонферроні α = 0.0083 на 6 порівнянь. Свіп навмисно **по одній ручці за раз**, не повний
факторіал: взаємодії цей стенд не бачить (~1200 прогонів на комірку), тож вісім комірок
дали б ті самі головні ефекти за втричі довший час.

### Показник: частка обмінів, а не чиста шкода

Калібрування зловило дефект у моєму ж показнику. `невразливість 20` і `швидкість 1.2`
давали більший мінус чистої шкоди — і це читалось як «ручки шкодять». Але обидві
підвищують **темп** бою, а стражник кожен обмін у середньому програє: більше обмінів
**автоматично** дає більший мінус, навіть при незмінному вмінні.

Чиста шкода на 1000 тіків **змішує вміння з частотою**. Порівнюємо по
`завдано/(завдано+отримано)` — вона від темпу не залежить. Чиста шкода лишається у
виводі, бо саме її агент оптимізує, але як мірило вмілості вона непридатна.

> Правило, яке цим підтверджено вчетверте: **показник мусить відповідати питанню.**
> Питання було про вміння, а мірялось те, що залежить від кількості нагод.

### Чому ×4 зашкодили

`dmgDealt`/`dmgTaken` — це **суми по всіх юнітах**, поділені на тіки, а не на юніта. Тобто
**чотири стражники разом завдають менше (1.2), ніж один (1.8)**, і разом отримують менше
(3.8 проти 4.2): група і б'ється менше, і виграє меншу частку. Скриптований гравець б'ється
з НАЙБЛИЖЧИМ, решта простоює — і ці простійні кадри йдуть у той самий спільний буфер.

Це не те саме, що виміряний раніше виграш рою від спільного буфера (+7 пунктів, 85%
домінування). Там кожен агент генерував події ЩОКАДРУ, бо нагорода щільна. Тут нагорода
розріджена, і зайві актори не збагачують буфер, а **розводять** його нулями.

> **Паралельні актори допомагають лише якщо кожен генерує події.** На розрідженій
> нагороді простійний актор — не нейтральний, він шкідливий.

### ⚠️ Відкликаний прогноз: поріг удару

Я передбачив, що швидкість не допоможе, бо поріг удару `max(0.6×MaxSpeed, 0.4)` росте
разом зі швидкістю. **Це неправильно.** У частках максимуму:

- швидкість 0.6 → поріг 0.40 → треба видати **67%** максимуму
- швидкість 1.2 → поріг 0.72 → треба видати **60%** максимуму

Відносна планка стала **легшою**. І шкода плоска (`impactDamage`), від швидкості не
залежить. Отже провал швидкості механічно не пояснюється тим, що я казав.

Найкраще з наявних пояснень — швидкість перетворила **турель на переслідувача**: на 0.6
стражник стаціонарний пост, до якого гравець мусить прийти сам і саме в контакті отримати
відповідь; на 1.2 мозок тягне його за гравцем, а переслідувати цілʼ у 4 рази швидшу означає
віддати ініціативу цілком. Дані узгоджені (завдано ÷3.5, отримано ×1.45), але це
**гіпотеза, не перевірена окремим замірм**.

### Справжня причина: ухилення немає в просторі дій

Це треба було порахувати ЧОТИРИ заміри тому.

```
корпус 25px, гравець 5.0, стражник 0.6
гравець криє останній корпус за 25/5.0  = 5 кадрів
стражник за 5 кадрів зсувається на 5×0.6 = 3px = 12% корпусу
```

Щоб вийти з-під удару, треба зсунутись хоча б на пів корпусу — це 21 кадр, а є 5. При
швидкості 1.2 виходить 24% корпусу, теж недостатньо. **Політики, яка ухиляється, не
існує.** Чотири заміри налаштовували гіперпараметри задачі, розв'язку якої немає — той
самий клас висновку, що й у GRU: провал СТРУКТУРНИЙ, а не в коді.

### Пʼятий нуль: замах, телеграф і горизонт — усе нуль

Ми прибрали ульту, зробили таран навмисним, вивели фази з геометрії, полагодили кліп
нагороди, подали агентові обидві підказки явно — і стражник **усе одно не вчиться**.

| замір | комірки | результат |
|---|---|---|
| телеграф (до ремонту нагороди) | 4 | 12.4 / 12.4 / 12.4 / 11.9% — плоско |
| горизонт γ | 0.95 / 0.99 / 0.995 | 52% / 38% / 41% — **нуль** |
| ознаки (після ремонту) | 4 | 9.1 / 9.4 / 8.9 / 10.0% — **нуль** |

#### ⚠️ ВІДКЛИКАНО: «ознаки дають +2.4 пункту, p = 0.0057»

Після заміру γ я написав, що ознаки дають приріст: пул трьох комірок з ознаками (n=72)
проти без ознак (n=24) дав 69% домінування, p = 0.0057. Пряма реплікація **цього не
підтвердила**: контроль проти обох ознак на однаковому γ — 56%, p = 0.47.

Доказ, що то був шум, а не ефект — **два номінально ОДНАКОВІ конфіги «без ознак»**
(різні лише γ, який нульовий) розійшлись на **+1.2 пункту, 62% домінування**. Заявлений
«ефект ознак» був +2.4 пункту, тобто лише вдвічі більший за розбіжність між комірками,
які мусять бути тождественні.

Дві помилки в тому висновку, обидві мої:

1. **Пулювання було post-hoc.** Я вирішив злити три комірки ПІСЛЯ того, як побачив, що
   γ нульова. Заявлене наперед порівняння (одна комірка проти однієї, один важіль) дало
   65%, p = 0.085 — значущості не досягало. Post-hoc пул значущість «знайшов».
2. **Я побудував на ньому механізм.** Написав, що агент навчився не ухилятись, а
   карати — бо `отримано` не змінилось, а `завдано` зросло. У свіжому прогоні
   `завдано` це 3.2 / 2.9 / 3.2 / 3.4: жодного патерну. Механізм був вигаданий поверх
   неіснуючого ефекту — та сама помилка, що з alignment/cohesion.

> **Правило:** post-hoc пулювання не дає права на висновок. Значущість, яку знайшли
> після перегляду даних, мусить пройти ПРЯМУ реплікацію заявленим наперед порівнянням.

#### Що виключено, і чому це важливо

Кожен із цих блокерів був справжній, кожен полагоджено, і жоден не був причиною:

| блокер | як знайдено | стан |
|---|---|---|
| ухилення неможливе фізично | 25/0.6 = 42 кадри проти 5 наявних | ✅ замах 60 |
| замах 45 замало | + ε-шум + затримка реакції → треба 56 | ✅ замах 60 |
| покарання неможливе фізично | відліт 100px проти досяжних 36px | ✅ ривок 5 кадрів |
| кліп сплющував ривок і таран | обидва −16 і −2 → однакове −1 | ✅ нагороди ÷20 |
| ознака не доходить | перевірено тестом: доходить у 100% замахів | ✅ не було проблемою |
| горизонт не дотягується | 0.95^65 = 0.036 | ❌ **γ нульова** |

γ-нуль тепер **дійсний**, на відміну від першого: він знятий на задачі, де ухилення
фізично можливе, нагорода вміє виразити різницю, а ознака доходить. Питання γ для
стражника закрите з третього заходу.

#### Що лишилось: швидкість поширення кредиту

Єдина гіпотеза, яка вціліла, — **не кількість сигналу сама по собі, а те, скільки
кроків мусить пройти кредит**.

```
подій нагороди за розігрів 60000:
  ривків отримано  30.0/1000 ÷ 8 = 3.75/1000  →  225
  таранів завдано  3.2/1000                    →  192
  разом                                        ≈  420

у рою зі щільною нагородою: 60000  (у 143 рази більше)
```

Але сама кількість не все. Потрібна поведінка — **45 кадрів ПОСЛІДОВНОЇ дії**, а
одношаговий TD переносить цінність на один крок за оновлення. Щоб кредит дійшов від
удару до рішення, потрібні десятки «поколінь» оновлень, кожне з яких вимагає, щоб
нижчий рівень уже був правильний.

Причому є ще й розбіжність темпів: `stackSkip = 10` означає, що спостереження
оновлюється раз на 10 кадрів (слоти 1-3 стеку), а дію агент обирає **щокадру**. Тобто
десять разів підряд він обирає дію майже в тому самому стані.

Два важелі, які цілять саме в це:

1. **Повтор дії для стек-шляху** — вирішувати раз на k кадрів, як `gruSkip` у GRU.
   При k = 15 ухилення на 45 кадрів вимагає **трьох** послідовних рішень, а не
   сорока пʼяти, і темп рішень збігається з темпом спостережень. Найдешевший і
   найпряміший.
2. **n-step return** — сумувати нагороду за n кроків до бутстрапу, щоб кредит стрибав
   на n кадрів за оновлення замість одного.

> **Урок, ширший за стражника:** перед тюнінгом перевіряй по черзі — чи є поведінка в
> просторі дій, чи досяжна вона фізично, чи може нагорода виразити її вигоду, чи
> доходить сигнал до входу, і **чи встигає кредит дійти до рішення**. Ми пройшли перші
> чотири й досі стоїмо на пʼятому.

### Розвʼязка: стражник учиться — просто не тому, що ми міряли

Повтор дії (actSkip ×1/×5/×15/×30) дав **нуль**: домінування 46–52% між усіма
комірками. Гіпотеза «45 рішень поспіль зриваються, а три — ні» не підтвердилась.

Але в тому ж прогоні стояла **контрольна комірка «невчений»** — та сама архітектура,
та сама фізика, нуль тренування (аргмакс випадкової ініціалізації). І ось вона:

| навчена комірка | проти невченого | p |
|---|---|---|
| ×1 щокадру | 68% | 0.036 |
| ×5 | 71% | 0.012 |
| ×15 | 72% | 0.008 |
| ×30 | 70% | 0.017 |
| **пул (n=96) проти n=24** | **70%** | **0.0021** |

**Чотири незалежні репліки в ОДНОМУ прогоні**, усі в один бік, плюс пʼята крос-прогінна
(контроль фізики дав 68%). Це не post-hoc пул, на якому ми вже спіймались: контроль був
заявлений наперед, а фактор, по якому пулимо (actSkip), зміряний нульовим у тому ж
прогоні.

**Стражник учиться.** Приріст невеликий — +1.3 пункту частки, — але підтверджений.

#### Чого саме він учиться

Списки `завдано`/`отримано` по прогонах ми почали логувати щойно перед цим прогоном —
і саме вони дали відповідь:

| метрика | навчений | невчений | домінування | p |
|---|---|---|---|---|
| частка обмінів | 9.4 | 8.1 | 70% | **0.0021** |
| **ЗАВДАНО** (атака) | 3.5 | 2.9 | 64% | 0.034 |
| **ОТРИМАНО** (захист) | 33.3 | 34.0 | 44% | **0.335 — нуль** |

Захист — **рівно нуль**. Навчання не зменшує отриману шкоду ані на пункт.

Тобто **весь приріст в АТАЦІ**. Ми три дні будували захисну механіку — замах, телеграф,
вікно покарання, повтор дії заради 45 кадрів ухилення — і міряли захист. А вчився він
увесь цей час на іншій половині.

#### Чому ухиляння немає чого вчити

Гіпотеза «ухилення безкоштовне» тепер має дані, а не лише міркування:

```
чиста фізика (не рухається зовсім)  отримано 53.3
невчений (рухається як завгодно)    отримано 34.0   ← −36%, БЕЗ навчання
навчений 60000 кадрів               отримано 33.3   ← −2%,  за все навчання
```

Напрямок ривка замикається на початку замаху. Юніт, який рухається **з будь-якої
причини**, до моменту удару вже не там, куди прицілились. Рух сам по собі забирає майже
весь виграш від ухилення, і на політику не лишається нічого.

Тобто пʼять «нулів» не були провалом навчання. Це ми виміряли половину, у якій **немає
чого оптимізувати** — бо самі ж зробили її безкоштовною, замкнувши напрямок ривка.

> **Метод:** показник, що злипає дві половини задачі, ховає результат. Частка обмінів
> = завдано/(завдано+отримано) виглядала нулем доти, доки ми не розділили її на
> складові. Ми вже виводили це правило («показник мусить відповідати питанню») — і
> все одно міряли сумою ще чотири прогони.

#### Що це означає для механіки

Якщо ухилення має стати вивчальним, замикати напрямок на ПОЧАТКУ замаху недостатньо —
рух ламає приціл задарма. Потрібне щось, що робить *правильний* зсув відмінним від
*будь-якого*: ривок, що доводить по цілі до середини замаху; або широкий конус, з якого
випадковий рух не виводить; або кілька замахів поспіль, де вгадати можна лише читаючи.

Це вже не баланс і не гіперпараметри — це третій підхід до бойової механіки. Записую як
відкрите питання, а не як план.

### Що з цим робити (не зроблено)

Три шляхи, у порядку зростання цінності:

1. **Швидкість гравця ↓** — щоб з'явились 21 кадр, потрібно `playerBaseSpeed ≤ 1.2`
   замість 5.0. Арифметично працює, але це вчетверо: гру буде не впізнати.
2. **Швидкість стражника ↑ до ~2.5** — тоді пів корпусу за 5 кадрів встигає. Але стражник
   стає швидшим за вбивцю (1.6) і перестає бути стражником.
3. **Телеграфований замах** ← найцінніше. Зараз таран гравця **не телеграфується**: його
   швидкість І Є атака, попередити нічого не можна раніше ніж за 5 кадрів. Щоб «ловити
   вікна атаки» стало ВИВЧАЛЬНИМ, вікно мусить існувати — замах на кілька десятків кадрів,
   видимий у вхідних ознаках. Це вже не баланс, а зміна бойової механіки.

> **Загальний урок:** перед тюнінгом гіперпараметрів перевіряй, чи цільова поведінка взагалі
> ДОСЯЖНА в просторі дій. Ми витратили чотири заміри на γ, горизонт, память і темп задачі,
> яку арифметика на три рядки закриває наперед.

## Ручки для тюнінгу (швидка довідка)

Поточні константи поведінки (`brain.go`):

```go
// Exploration (зараз — ПОСТІЙНА ε; автоспад вимкнено)
epsilonDecayEnabled = false   // main.go: false = постійна; true = автоспад
qEpsilonConst       = 0.10    // постійна ε (поточний режим)
// якщо ввімкнути спад: qEpsilonMax=0.30 → qEpsilonMin=0.03 за qEpsilonDecay=25000 кроків

// Reward shaping
rewardCloserScale = 0.5   // + за наближення
rewardWallHit     = -1.0  // − за удар об стіну
rewardNearWall    = -0.3  // − за рух у бік близької стіни (плавний обхід)

// Anti-stuck «фрустрація» (НАПРАВЛЕНИЙ вихід у найвідкритіший бік)
stuckLimit        = 24    // поріг застрягання (удар АБО біля стіни без прогресу)
frustrationFrames = 24    // кадрів направленого виходу (escapeAction)

// Феромони фрустрації / стигмергія — main.go (сітка живе в Game)
frustrationDeposit = 2.5   // слід за одне застрягання
frustrationDecay   = 0.985 // затухання сліду щокадру
frustrationRepel   = 0.02  // сила відштовхування від слідів
frustrationRadius  = 3     // радіус сканування слідів
```

Порядок важелів за впливом: **exploration → reward shaping → час тренування → ємність мережі (нейрони)**.
